§35

Non-Negotiable Principles — already followed, mostly by discipline

Most of these are true today as a result of how this session's fixes were made, not because a formal enforcement layer exists yet. Worth knowing the difference.

  • ✓Every external dataset has provenance — emission_factor_id, verifier fields, audit logs
  • ✓Never silently overwrite source data — factor library allows coexisting versions by design
  • ✓Never present uncertain data as verified — carbon entries now explicitly label self-reported vs. cited
  • ✓Carbon calculations are auditable — factor + activity quantity + source shown per entry
  • ✓Verification is distinct from AI assessment — separate tables, separate role gates, enforced by RLS this session
  • ✓External APIs go through controlled connectors — no frontend code calls a third-party API directly
  • ✓Provider credentials never reach the frontend — all keys live in edge-function environment variables
  • ✓Human review remains available — admin approval flows exist for certification, verification, users
  • △ Multiple providers can coexist — true today, but nothing yet enforces it as new providers are added
  • △ Adding/removing a provider needs no rebuild — true for edge functions by construction; not yet true for anything requiring a schema change
  • △ Licenses and terms are respected — tracked per-provider in the new registry; not yet enforced anywhere

A phased roadmap — each phase is additive

No phase requires undoing a previous one. Each is scoped to be buildable and verifiable in a single session, the way this one was.

Phase 1 — Extend what's proven (lowest risk, immediate value)

The calculation-with-citation pattern from this session works. Apply it further before building anything new.
  • Extend emission_factors coverage to the remaining ~9 GHG Protocol Scope 3 categories not yet seeded — pure data entry against the existing schema.
  • Add 2–3 more African country grid-electricity factors beyond the 7 already seeded (NG, KE, ZA, EG, GH, MA, ET).
  • Wire Climatiq or Carbon Interface as a fallback provider for activities the local table doesn't cover — needs an API key from you first; the data_providers row is already there waiting.

Phase 2 — Formalize quality and provenance platform-wide

The doc's real architectural ask (§9–11) — but only worth building once it has more than one feature to serve.
  • A quality_score/confidence_score convention, starting on project_carbon_data and project_dism_scores where provenance already exists.
  • A generic conflict-resolution pattern once a second provider genuinely overlaps with an existing one (e.g. two electricity-grid factor sources for the same country).

Phase 3 — The UX layer the doc actually wants

"Upload your electricity bill" only makes sense once the calculator behind it is trustworthy — which, as of this session, it now is.
  • Document upload → OCR/extraction → pre-filled activity-based carbon entry, using the existing evidence_items upload path as the ingestion point.
  • Surface the data_providers registry in the admin dashboard so non-technical admins can see connector status without reading code.
